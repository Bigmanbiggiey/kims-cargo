# Acceptance Criteria

Use this as the definition of done. Mark each criterion Pass / Fail / Blocked / Not Tested and attach evidence.

## A. Project and documentation

- [ ] Approved architecture and key decisions documented.
- [ ] Setup instructions work on the target development environment.
- [ ] No secrets committed; `.env.example` contains placeholders only.
- [ ] Scope, dependencies, third-party costs, and exclusions documented.
- [ ] Git status is clean at the agreed delivery point, or all remaining changes are explained.

## B. Public website

- [ ] Required company, services, fleet, service-area, quote, and contact information is accessible.
- [ ] Layout works at narrow mobile, tablet, and desktop widths.
- [ ] Navigation, buttons, phone links, WhatsApp links, and internal links work.
- [ ] No placeholder text, invented specifications, broken images, or unapproved claims remain.
- [ ] Client has approved English/Swahili wording and all public contact details.
- [ ] Fleet details are limited to client-verified facts.
- [ ] Map/routes do not block essential content when third-party maps fail or are unavailable.

## C. Quote enquiry and calendar

- [ ] All approved required fields are present and labelled accessibly.
- [ ] Pickup, destination, cargo details, and estimated size/weight can be entered.
- [ ] Preferred date and time/time window can be selected and submitted.
- [ ] Invalid input is rejected with understandable feedback.
- [ ] Past dates are blocked if that is the approved rule.
- [ ] Server-side validation exists wherever a server endpoint receives submissions.
- [ ] Proportionate spam/rate controls are tested.
- [ ] Successful submissions reach the agreed notification destination, demonstrated by a real test.
- [ ] Failure states do not falsely tell users that an enquiry was delivered.
- [ ] Customer acknowledgement works as approved.
- [ ] Submission details and credentials are not exposed in public logs or client-side bundles.
- [ ] Wording clearly says the requested date/time is a preference and the company must confirm availability.

## D. Quality and launch

- [ ] Build passes.
- [ ] Lint/type checks/tests pass where configured.
- [ ] Keyboard navigation, focus visibility, labels, and error messages are checked.
- [ ] Basic metadata, indexing directives, and sitemap/robots settings are correct for intended launch.
- [ ] Images and scripts are optimized appropriately.
- [ ] Production deployment and HTTPS are verified, if deployment is in scope and authorized.
- [ ] Form tested in production using a controlled test submission.
- [ ] Client receives access/handover documentation and understands recurring costs.
- [ ] Known limitations and post-launch support terms are documented.

## E. Business acceptance

- [ ] Final deliverable stays within approved KES 50,000 scope or has a signed change approval.
- [ ] Client confirms page content, contact methods, service claims, and fleet details.
- [ ] Client receives source code/handover after final payment, as agreed.
- [ ] Domain and critical accounts remain client-owned where possible.
